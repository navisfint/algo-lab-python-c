# 三个实验的 Python / C 实现与设计思想对比

> 实验来源：Python 程序设计实验（约瑟夫环 · 轮盘抽奖 · 蒙提霍尔悖论）
> 环境：Python 3.13.14 ／ MSVC 19.39 (`cl.exe`, x64)，零告警编译
> 结论均来自**实际运行**，非推演

---

## 0. 结论先行

**1. 三个实验的计算逻辑与语言无关，差别在「数据怎么装、内存谁管、错误怎么报」。**
Python 用内置高级容器 + 异常，C 用数组 / 结构体 + 返回值——这是两套完全不同的成本模型。

**2. 算法选择对性能的影响，远大于语言选择。** 实验一实测（n=20000, k=3）：

| 实现 | 复杂度 | 耗时 |
|---|---|---|
| Python 列表切片 | O(n²) | 0.8955 s |
| **C 数组 memmove** | **O(n²)** | **0.1080 s** |
| **Python 迭代器法** | O(n·ln n) | **0.0228 s** |
| C 数组环形标记 | O(n·ln n) | 0.0020 s |
| C 循环链表 | O(n·k) | 0.0010 s |
| Python 数学递推 | O(n) | 0.0007 s |
| C 数学递推 | O(n) | ≈0.0000 s |

> **Python 用对算法（0.0228 s）反而比 C 用错算法（0.1080 s）快 5 倍。**
> 换语言只拿常数级提速，换算法才降复杂度——这是三个实验里最值钱的一条。

**3. C 的代价是「正确性全靠自己守」。** 本次 C 版踩到一个**数组越界却"碰巧算对"**的坑，
靠 1000 组交叉对拍才暴露（见 §6）；同样写法在 Python 里会直接抛 `IndexError`。

## 2. 实验一 · 约瑟夫环

**建模**：圈 = 有序容器 ；每轮动作 = 「报数 k 次 → 出圈 → 从下一位继续」；终止 = 剩 1 人。

```
n 人围圈 ──> 报数 1..k ──> 第 k 人出圈 ──> 圈缩小 ──┐
   ↑                                              │
   └────────── 人数 > 1 就继续 ◄───────────────────┘
                          人数 == 1 ──> 输出幸存者编号
```

**实测结果**（n=10, k=3）出圈顺序 `3 → 6 → 9 → 2 → 7 → 1 → 8 → 5 → 10`，**最后留下 4 号**。
n=20000, k=3 时幸存者为 **19037**，两种语言三种方法完全一致。

| 一致性验证 | 结果 |
|---|---|
| Python 三方法（n≤200, k∈{1,2,3,5,7}，1000 组） | 全部一致 ✔ |
| C 四方法（同 1000 组） | 全部一致 ✔ |
| Python ↔ C 结果 | 一致 ✔ |

**优劣分析（实测支撑）**

| 方法 | 优点 | 缺点 |
|---|---|---|
| 列表切片 / 数组 memmove | 代码最直观，存活者始终稠密、无空转 | 每次删除搬移 O(n)，整体 O(n²)，**n=20000 时慢 40~50 倍** |
| itertools.cycle / 数组环形标记 | 无数据搬移，绝对耗时最低的模拟法 | 已出局者仍被迭代到，只能跳过（期望 n·ln n 次空转） |
| 循环链表（C 独有） | 语义上最贴"围成一圈"，删除即摘链 | 每个结点多一个指针开销；**必须逐个 `free`**，漏一个就泄漏 |
| 数学递推 | O(n) / O(1)，n 再大也是毫秒级 | **不能输出游戏过程**，且无法直接推广到"每次 k 变化"的变体 |

## 3. 实验二 · 模拟轮盘抽奖

**建模**：把"轮盘"抽象成一张 **角度区间 → 奖项** 的表（表驱动：改规则只改表，不改逻辑）。

| 奖项 | 扇区 | 理论概率 | Python 实测(10000) | C 实测(10000) |
|---|---|---|---|---|
| 一等奖 | [0°, 30°) | 8.33% | 7.94% | 7.94% |
| 二等奖 | [30°, 108°) | 21.67% | 22.23% | 21.48% |
| 三等奖 | [108°, 360°) | 70.00% | 69.83% | 70.58% |
| **合计** | 360° | 100.00% | 10000 次 | 10000 次 |

偏差均在 ±0.6% 以内，符合 `1/√n` 量级的抽样波动。

**要点**
- `randrange(360)` 上界取不到 360，所以右端点写开区间 `[108, 360)` 才严谨（教材参考代码同理）。
- 教材版「字典遍历 + 区间线性匹配」O(m)；拓展版「累积度数 + 二分查找」O(log m)，扇区多了才划算。
- **同一随机种子下 Python 与 C 的结果不同，这是正常的**——两者用的不是同一个伪随机数发生器。

## 4. 实验三 · 蒙提霍尔悖论

**建模**：门表（数组/字典）→ 玩家选门 → 主持人过滤出「非所选 且 是羊」的门并打开 → 玩家决策 → 揭晓。

**实测结果**（10 万局，玩家随机选门）

| 策略 | Python | C | 理论 |
|---|---|---|---|
| 坚持原选择 | 33551 局 / 33.55% | 33317 局 / 33.32% | 33.33% |
| 换门 | 66449 局 / 66.45% | 66683 局 / 66.68% | 66.67% |

**悖论的关键**：主持人开门**不是随机的**——他必然开一扇羊门，这个动作携带信息。
玩家初选命中汽车的概率只有 1/3，**另外 2/3 的概率全部"压缩"到了剩下那扇门上**，所以换门胜率翻倍。
代码里也验证了：两策略胜局数之和恒等于总局数（每局必有一方赢，二者互补）。

## 5. Python vs C 设计思想对照

| 维度 | Python | C | 设计思想差异 |
|---|---|---|---|
| **数据容器** | `list` / `dict` / `set` 开箱即用 | 数组、`struct`、链表全部手写 | Python 给"语义化容器"（按语义选结构）；C 只给"连续内存"（按内存布局选结构） |
| **"一圈"怎么表达** | `list` 摊平 + 取模，或 `cycle()` 无限迭代器 | 数组 + 取模，或 `next` 指针首尾相接 | Python 用**协议**表达环形；C 用**指针**表达环形 |
| **删除一个元素** | `pop` / 切片 / 翻标记位 | `memmove` 搬移 / 翻标记位 / `free` 摘链 | Python 的"删除"是语义操作；C 必须显式表态是"搬、标、还是释放" |
| **内存管理** | 引用计数 + GC，自动回收 | `malloc`/`calloc`/`free` 全程手工 | 实验一 C 版 5 处分配、5 处释放，漏一处就泄漏 |
| **遍历** | `for`-`in`、迭代器协议、`next()` | `for(i=0;i<n;i++)`、下标算术 | Python 抽象"取下一个元素"；C 抽象"地址偏移" |
| **错误处理** | `try/except` + `assert`，正常流与异常流分离 | 无异常，靠返回值 + 重试循环 | 同一个"防非法输入"目标，C 把错误码混进了正常控制流 |
| **随机数** | `random` 模块 MT19937，`randrange()` 无偏 | `rand()` 实现自定（MSVC 是 LCG，`RAND_MAX` 仅 32767） | Python 把"随机数质量"当标准库承诺；C 当实现细节，用错 `rand()%360` 会把低位偏差放大 |
| **数值类型** | 任意精度 `int`，不会溢出 | `int` 固定宽度，`i + k - 1` 可能溢出 | 本轮 n 小看不出；n 到 10⁹ 量级时 C 必须换 `long long` |
| **字符与编码** | 源码默认 UTF-8，`str` 即 Unicode | 源码编码 / 执行字符集 / 控制台代码页三方割裂 | 本次 C 源码必须加 UTF-8 BOM，否则 MSVC 报 C4819；输出改用英文避免乱码 |
| **代码量 / 可读性** | 核心逻辑约 200 行，接近伪代码 | 约 350 行，多出内存与校验样板 | C 样板多，但控制更细、行为更可预测 |
| **性能** | 解释执行，常数因子大 | 编译优化后常数因子小 | 同算法下 C 快 8~11 倍（见 §0 实测） |

## 6. 三个实验共通的建模思路

**同一个骨架**：**状态 → 状态转移 → 终止条件**。三个实验都能套进这句话：

| 实验 | 状态 | 转移 | 终止 |
|---|---|---|---|
| 约瑟夫环 | 圆圈中存活的人 | 报数 k 次 → 出圈 | 只剩 1 人 |
| 轮盘抽奖 | 指针角度 | 随机取角 → 落入某扇区 | 试玩次数用尽 |
| 蒙提霍尔 | 门后奖品 + 玩家选择 | 开门 / 换门 | 揭晓输赢 |

**两条通用手法**
1. **表驱动**：把"规则"从"代码"里抽出来（扇区表、门表），改规则不动逻辑 —— Python 用 `dict`、C 用 `struct` 数组，殊途同归。
2. **模拟 vs 解析**：实验一给出了最干净的对照 —— 模拟法 O(n·ln n) 且能打印过程，解析法 O(n) 但拿不到过程。"能观测"和"最省时"往往不可兼得，先想清楚要哪个。

## 7. 两个真实的坑（都是"看起来对、其实无效"）

**坑 1（C，危险）**：`sim_array_ring()` 里初始化数组用的是循环变量 `i`，循环跑完 `i == n`，
第一次 `while` 却直接用 `alive[i]` 读了 `alive[n]` —— **堆越界读写**。
它没有崩，而是在 n=10, k=3 时"碰巧"算出了正确答案，一直瞒到跨 1000 组对拍才露出来。
> 教训：C 里的"结果对"不等于"代码对"。**只有交叉验证（对拍）才能证明实现正确**，单点测例会骗人。

**坑 2（Python，隐蔽）**：实验二两种实现共用一条随机流，第二次统计前**忘了重新播种**，
导致两张结果表对不上，一度让人怀疑"两种判区逻辑不等价"。
> 教训：凡是"同一输入下应完全一致"的对比，必须让两边从**同一个起点**出发；共享可变状态（随机流）是最容易被忽略的那个起点。

## 8. 一句话总结

| 问题 | 答案 |
|---|---|
| 两个语言"做的事"一样吗？ | 完全一样，算法与逻辑可 1:1 映射 |
| 那差别在哪？ | **数据承载方式、内存责任归属、错误表达机制**——Python 用容器和异常买省心，C 用样板代码换可控 |
| 该选哪个？ | 要快速验证想法 / 处理复杂数据结构 → Python；要吞吐、要确定性的内存与时间 → C |
| 最该记住的一条？ | **先把算法选对，再谈语言。** 选错算法，C 也会被 Python 吊打 |
